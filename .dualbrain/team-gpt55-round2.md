Below is the critique I would give as GPT-5.5 reviewing Opus 4.7’s simplified Cortex architecture. The short version: Opus is right to fear over-modeling, especially before first production use. But several of the proposed simplifications collapse different failure modes into the same bucket. That is fine for a prototype with one repo, one team, and low concurrency. It starts failing once Cortex becomes an actual orchestration engine where multiple agents, humans, branches, repos, and release gates interact asynchronously.

The central architectural question is not “can we make the model smaller?” It is “which distinctions are operationally necessary before damage occurs?” In Cortex, some distinctions are not polish. They are control-plane safety.

## 1. Conflict Detection

Opus proposes two layers: path overlap and branch/diff. Four impact levels: `Read`, `Edit`, `Exclusive`, `ContractChange`. Five named severity levels instead of numeric scores. Simple path-based leases with three modes. No merge train.

This is attractive because path overlap is easy to explain, easy to persist, and easy to debug. It also maps well to Git’s native conflict surface. But it is not enough for AI orchestration.

The main thing Opus gets wrong is treating source files as the unit of conflict. In real software systems, files are often a poor proxy for ownership, behavior, or release risk. The same behavioral contract can span many files, and two agents can break each other without ever touching the same path. Conversely, two agents can edit the same file safely if they touch isolated symbols or declarative entries. A path-only model is simultaneously too coarse and too blind.

At 5 users, path overlap mostly works if the system is young, the repos are small, and the agents are working on obviously separate areas. You may see annoying false positives: one agent editing `src/routes.ts`, another adding a route; one editing `package.json`, another adding a script; one updating a docs index, another updating a page. The simple lease system will serialize work that could have proceeded in parallel. That is inefficient, but survivable. The bigger issue even at 5 users is false negatives: one agent changes a database helper, another changes billing logic that relies on its old rounding semantics. No path conflict, no diff conflict, but a real production bug.

At 20 users, the false positives become workflow damage. Common files become permanent bottlenecks: route registries, schemas, migrations, package manifests, generated clients, shared config, API definitions, type exports, auth middleware, billing utilities, deployment scripts. If Cortex only knows paths, the system will over-lock hot files and under-detect semantic conflicts. People will route around it. They will either take overly broad exclusive leases “just in case,” or ignore conflict warnings because too many are noisy. Both are bad: one kills throughput, the other kills trust.

At 100 users, path-only conflict detection becomes a governance failure. The system will not be able to distinguish harmless parallel edits from dangerous cross-cutting contract changes. It will also fail to explain conflicts in terms that match human review: “both touched `src/db/index.ts`” is much less useful than “one change alters the transaction boundary for credit debits while another adds a consumer assuming the old atomicity.” Production incidents at that scale rarely come from simple textual merge conflicts. They come from incompatible assumptions that pass Git merge cleanly.

The missing symbol layer matters because symbols are often the smallest useful unit of coordination. Functions, types, classes, endpoints, database tables, events, and exported constants form the API surface inside a repo. If Cortex cannot say “agent A is changing `round6()` and agent B is changing all credit settlement callers,” it cannot prioritize correctly. It will either lock the whole file or miss the behavioral dependency.

The missing domain layer matters because not all paths have equal operational meaning. In ClawNet-like systems, billing, auth, credential trust, deploy, and Soma verification are not just directories. They are risk domains. A change in `src/billing/credits.ts` and a change in `src/routes/usage.ts` may be tightly coupled even if they live apart. A change in `docs/reference/billing.md` may be contractually relevant to the code. A domain model lets Cortex ask: is this a billing semantics change, an auth boundary change, a protocol integration change, or a UI-only change? Without that, severity is too shallow.

The missing contract layer is the most dangerous omission. Contracts are where production failures hide: API request/response shapes, database schema, event formats, auth claims, payment webhook semantics, CLI flags, environment variables, deployment invariants, generated SDKs, and protocol specs. A branch can merge cleanly and still break every consumer. Path overlap does not catch “renamed JSON field used by another repo,” “changed migration order,” “tightened auth middleware in a way that blocks CI deploy,” or “changed expected Soma credential semantics.” Contract-aware detection is not gold plating; it is how orchestration avoids shipping incompatible slices.

Opus’s four impact levels are also too compressed. `ContractChange` is doing too much work. A contract change can be additive, narrowing, breaking, experimental, internal-only, external, reversible, migration-backed, or release-blocking. Treating all of those as one impact level forces the severity system to carry information it does not structurally know. A non-breaking optional field addition and a required field removal should not share the same impact category.

The five named severity levels are good for presentation, but not enough for computation. Humans like named levels. Schedulers, queues, policies, and risk budgets need finer granularity. A 0-100 score is not inherently better, but a richer risk vector is. Cortex should be able to combine dimensions: blast radius, confidence, reversibility, domain criticality, active dependents, test coverage, lease contention, and deploy proximity. A named level can be derived from those inputs for display. If Opus removes the underlying dimensions entirely, Cortex loses explainability and prioritization.

Simple path-based leases with three modes are fine as the first enforcement primitive. But they should not be the only model. Leases need to express intent and scope at a level that matches risk: symbol lease, domain lease, contract lease, migration lease, release lease, and generated artifact lease. A path lease on `openapi.yaml` does not explain whether the agent is adding an endpoint, removing a field, or regenerating output. A contract lease can.

No merge train is defensible for v1 only if Cortex is not doing high-concurrency automated integration. But no merge train becomes painful quickly. At 5 users, manual merge order is okay. At 20 users, “green when tested” becomes misleading because several branches are concurrently green against the same base but not green together. At 100 users, without a merge train or equivalent integration queue, Cortex will create a stream of speculative branches that invalidate each other after approval. The result is rebase churn, flaky confidence, and human frustration. A merge train prevents a real failure mode: N approved changes all individually pass, but the third merged change breaks the fourth, and nobody notices until after deploy.

Where Opus is right: start with path overlap, branch/diff inspection, and simple lease modes. Do not build a perfect semantic conflict engine before Cortex has real workloads. But the data model should not make richer detection impossible. The mistake would be hardcoding “conflict equals path plus diff” as the permanent truth. Ship simple detectors behind an extensible conflict graph: path conflicts now, symbol/domain/contract detectors later, with a common evidence model.

## 2. Cross-Repo

Opus proposes `SubGoal`s with `CrossRepoDep` edges instead of a typed DAG. Artifact kinds are freeform strings with runtime JSON validation instead of typed enums. There are three step types: `Repo`, `CrossRepoContract`, and `HumanGate`. Release policy is only `AtomicPreferred`.

The good instinct here is avoiding an over-specified workflow engine. Cross-repo orchestration systems often die by trying to model every possible dependency before the first real multi-repo release. But Opus’s design loses too much semantic information at the exact place where Cortex needs precision.

Cross-repo work fails differently from single-repo work. The hard problems are dependency direction, compatibility windows, version skew, rollback order, contract ownership, evidence, and partial rollout. A generic `CrossRepoDep` edge tells you that one thing depends on another. It does not tell you whether the dependency is a build-time dependency, runtime dependency, API compatibility dependency, migration dependency, feature-flag dependency, security review dependency, release ordering dependency, or documentation truth dependency. Those distinctions determine what Cortex is allowed to do.

At 5 users, `SubGoal` plus `CrossRepoDep` may work because the team can keep the meaning in their heads. “Pulse needs Soma’s credential rotation spec before ClawNet integration” is understandable in a meeting. A freeform artifact kind like `"soma-spec"` or `"api-contract"` is survivable when the same few people read all of it. Runtime JSON validation can catch malformed artifacts if validators exist and are maintained.

At 20 users, the weak typing starts to rot. Different agents and humans will name artifacts inconsistently: `openapi`, `OpenAPI`, `api_schema`, `contract`, `contract-v2`. Some artifacts will have validators, others will not. Some `CrossRepoDep`s will mean “must merge before,” others “must be reviewed with,” others “must not deploy until.” If the edge type does not encode this, Cortex cannot schedule, block, warn, or recover correctly. The system becomes a note-taking layer, not an orchestration engine.

At 100 users, freeform artifact kinds become a data governance problem. You cannot reliably query: “show every breaking contract change waiting on downstream consumers,” “show all migrations that require atomic deploy,” “show all repos blocked by a Soma protocol decision,” or “show all artifacts whose schema validator changed since approval.” Runtime validation is useful, but only if the system knows when validation is required and what policy attaches to the artifact kind. Freeform strings make policy discoverability weak.

The typed DAG matters because cross-repo work needs machine-checkable semantics. A typed edge can represent `produces`, `consumes`, `blocks`, `must_precede`, `compatible_with`, `rolls_back_after`, `requires_human_approval`, `requires_spec_decision`, or `gates_release`. A typed node can represent repo change, spec artifact, migration, generated client, deploy step, manual approval, feature flag, external dependency, or verification evidence. This is not academic modeling. It lets Cortex answer operational questions automatically.

For example: Soma changes a credential format. ClawNet needs to consume it. Pulse may display related status. A simple `CrossRepoDep` edge says ClawNet depends on Soma. But Cortex needs to know more. Is Soma’s change merged? Is the protocol spec accepted? Is the ClawNet consumer backward-compatible with old credentials? Does production deploy order matter? Can ClawNet ship dormant support before Soma deploys? Does rollback require reverting Soma first or ClawNet first? `AtomicPreferred` alone cannot answer that.

Opus’s three step types are too few. `Repo`, `CrossRepoContract`, and `HumanGate` omit migrations, deploys, generated artifacts, environment preparation, feature flags, external service configuration, data backfills, security review, and validation runs. You can cram those into `Repo` or `HumanGate`, but then Cortex cannot reason about them. A data migration is not just a repo step. A feature flag flip is not just a human gate. A generated SDK is not the same as a contract. These differences affect order and rollback.

The single release policy `AtomicPreferred` is particularly risky. Cross-repo releases are not all atomic-preferred. Some are atomic-required because version skew is unsafe. Some are staged-required because atomic release is impossible or riskier. Some are independent with compatibility checks. Some are producer-first, some consumer-first, some expand-contract, some dual-write-read-new, some flag-gated. If Cortex only has `AtomicPreferred`, it cannot tell whether partial deployment is acceptable. At small scale, humans remember. At large scale, this causes incidents.

What breaks at 5 users: mostly ambiguity. A cross-repo task gets marked done because all `SubGoal`s are complete, but the actual contract was not accepted or downstream was not deployed. This is manageable if the same person reviews everything.

What breaks at 20 users: scheduling and release order. Agents will open PRs in multiple repos without knowing whether the dependency is blocking, advisory, or release-order-specific. Human reviewers will become the true orchestrator, which defeats Cortex’s purpose.

What breaks at 100 users: auditability and rollback. During an incident, “what changed across repos and what depended on what?” must be answerable from structured data. Freeform artifacts and generic edges will not be enough. You need typed dependencies and release policies to reconstruct intent and decide rollback order.

Where the richer design prevents failures: it can block a breaking producer change until at least one downstream consumer has compatibility support; it can require an ADR before protocol semantics change; it can detect when docs claim a contract that code does not implement; it can enforce that migrations deploy before code or vice versa; it can mark partial release as forbidden for certain dependency types; it can produce an incident timeline from the DAG.

Where Opus is right: avoid building a general-purpose BPMN clone. The v1 should have a small set of typed nodes and edges based on real Cortex workflows. But “typed” does not mean “huge.” A practical compromise is a minimal typed DAG with an `extension` escape hatch. Keep freeform metadata, not freeform semantics. Unknown artifact kinds can exist, but policy-bearing artifact kinds should be registered.

## 3. Chat

Opus proposes three thread types: `Goal`, `Conflict`, and `Review`. No presence system. Simple `Normal`/`Urgent` priority. No compaction. Questions never block Brain.

The good part is resisting Slack clone gravity. Cortex chat should not become a generic messaging product. It should be task-native coordination: decisions, questions, reviews, conflicts, and evidence attached to orchestration state. But Opus oversimplifies the lifecycle of communication in an AI orchestration engine.

The most dangerous claim is “questions never block Brain.” If Brain means the central planning/execution loop, then some questions absolutely must block specific actions. Not every question should block global reasoning, but uncertainty about destructive, irreversible, security-sensitive, billing-sensitive, or contract-changing actions must be able to block execution. Otherwise Cortex will proceed through ambiguity and create exactly the kind of autonomous-agent risk teams are worried about.

The right distinction is not “questions block Brain” versus “questions never block Brain.” The distinction is scope. A question can block a step, a lease, a repo, a release, a contract edge, or a goal. Brain can continue planning around it, executing independent work, and refining alternatives. But the unsafe action must not proceed until the gate resolves. Opus’s design throws away scoped blocking because it wants to avoid deadlocks. That is the wrong tradeoff. You avoid deadlocks with timeouts, escalation, fallback plans, and dependency scoping, not by making all questions non-blocking.

At 5 users, no presence is acceptable. Everyone knows who is around. Normal/Urgent priority is enough. No compaction is okay because threads are short. Thread types `Goal`, `Conflict`, and `Review` likely cover most early communication.

At 20 users, coordination starts failing. Without presence or availability signals, Cortex will route urgent questions to people who are offline, in another timezone, or not the right owner. Without richer priority, everything that matters becomes `Urgent`. Without scoped blocking, an agent may keep working past an unresolved approval question. Without compaction, long goal threads become unreadable and agents waste context re-reading stale discussion.

At 100 users, chat without lifecycle semantics becomes a liability. Cortex needs to know which messages are decisions, which are questions, which are approvals, which are objections, which are evidence, which are superseded, and which are still active. Plain threads do not scale as the coordination substrate for autonomous work. People will miss decisions. Agents will cite old messages. Reviews will be reopened because the canonical answer is buried in hundreds of lines.

The lack of compaction is especially problematic for AI systems. Human chat can be searched. Agent context has a budget. If Cortex uses chat history as part of planning or execution context, it needs durable summaries, decision extraction, stale-state marking, and links back to evidence. Otherwise the system either drops important context or carries too much irrelevant context. Both lead to mistakes. Compaction is not just a UX feature; it is memory hygiene.

The three thread types omit several operationally meaningful categories: decision, question, incident, release, handoff, design review, security review, migration gate, and customer-impact note. You do not necessarily need all of those as top-level thread types, but Cortex needs structured message or thread states to represent them. A `Review` thread that contains a security approval and a code style comment should not treat both as equivalent.

Simple `Normal`/`Urgent` priority also collapses important distinctions. Priority should separate urgency from severity from blocking status. A low-severity question can be urgent because it blocks a deploy. A high-severity architectural concern may not be urgent if it is for next quarter. A security concern may be high severity even if not immediately blocking. Two labels cannot encode that.

No presence system is understandable for v1, but at least ownership and notification state are needed. Presence does not have to mean live typing indicators or green dots. For Cortex, useful presence means: who is assigned, who is on call, who can approve this domain, who last acknowledged, what timezone or schedule applies, and whether escalation is needed. Without this, human gates become unreliable.

Where the richer design prevents production failures: it blocks a payment contract change until the billing owner approves; it prevents a stale chat answer from being treated as current after an ADR supersedes it; it escalates an urgent deploy gate to the right on-call instead of waiting on someone unavailable; it summarizes a 200-message conflict thread into the current decision and unresolved objections; it marks a question as blocking only the risky step while allowing independent work to continue.

Where Opus is right: do not build a generic enterprise chat system. Start with goal, conflict, and review threads if that matches the core workflow. Avoid presence theater. Avoid making Brain globally pause for every unanswered question. But implement scoped blocking questions, durable decisions, and compaction earlier than Opus suggests. Those are not social features; they are orchestration correctness features.

## 4. Map

Opus proposes hierarchical `OrgMap`, `RepoMap`, and `GoalMap`, with four or five node types and three or four edge types per level. No `ViewportHints`. SSE updates.

The good instinct is that maps should be comprehensible. A single universal graph with dozens of node and edge types can become unusable. Hierarchical maps match how humans think: organization, repository, goal. SSE is also a reasonable v1 transport: simpler than bidirectional websockets and enough for server-driven updates.

The problem is that Cortex’s map is not only a visualization. It is an operational model. If the map is too sparse or too rigid, it becomes decorative instead of useful. The map must support navigation, scheduling, ownership, risk, conflict explanation, release readiness, and cross-repo reasoning. A minimal hierarchy can hide exactly the relationships users need to see.

At 5 users, the proposed hierarchy probably works. Users can browse org-level state, drill into a repo, then inspect a goal. A few node types are enough. SSE can push updates. No viewport hints is fine because maps are small.

At 20 users, visual overload and missing context appear. The org map may have many active goals across repos. The repo map may have branches, PRs, conflicts, leases, tests, deploys, and owners. The goal map may have subgoals, agents, artifacts, questions, reviews, and dependencies. If the node and edge types are too few, important distinctions collapse. If there are no viewport hints, the UI may render the wrong slice: too much noise, wrong zoom level, unstable layout, or missing hotspots.

At 100 users, map usability becomes a scaling feature. A graph that technically contains the data but cannot guide attention is not useful. Users need the map to answer: what is blocked, what is risky, what changed since I last looked, what needs my action, what is near release, what conflicts with my work, what depends on this contract, and what will break if this repo deploys now? A simple hierarchy does not automatically provide those views.

No `ViewportHints` sounds minor, but it matters. Graph layout is expensive and subjective. The server often knows the semantic importance of nodes: current user’s tasks, blockers, critical path, high-risk domains, recently changed nodes, active conflicts, hidden dependencies, recommended drilldowns. If the client must infer all of that from raw graph structure, the UI will be inconsistent and noisy. `ViewportHints` do not have to be complex. They can be server-provided suggestions: focus node, pinned clusters, collapsed groups, priority bands, recommended filters, changed-since markers, critical path, and offscreen alerts.

Without hints, a 100-user org map can become a hairball. Users will stop using it and fall back to lists. That is acceptable if lists are the intended primary UI. But if Cortex sells the map as a core coordination surface, it needs attention guidance.

The limited node and edge types are also risky across levels. An org-level dependency is not the same as a repo-level dependency or a goal-level dependency. A repo “depends on” another repo at runtime; a goal “depends on” another goal for release order; an artifact “depends on” a spec for truth. If the map uses the same few generic edge types everywhere, it may look clean but become semantically vague. If it uses separate types per level, it needs enough types to encode policy-bearing relationships.

SSE updates are fine for many cases, but Cortex should be clear about what kind of real-time behavior is required. SSE is server-to-client only. If clients only need to receive map updates and send mutations via normal HTTP, SSE is simpler and robust. At 100 users, SSE can still work, but the system needs topic filtering, backpressure, reconnect semantics, event replay IDs, and authorization filtering. Otherwise each client receives too much, misses updates during reconnect, or sees data it should not. The issue is not SSE itself; it is treating SSE as “simple updates” without event discipline.

Where Opus is right: the map should not begin as a maximal knowledge graph. Hierarchical maps are easier to ship and easier to explain. Keep the v1 vocabulary small. Use SSE unless there is a demonstrated need for collaborative low-latency bidirectional behavior. Avoid visual cleverness before users know what they need.

Where the richer design prevents failures: viewport hints help a release manager see the actual critical path instead of a generic graph; typed map edges distinguish runtime dependency from release blocker; map deltas show that a contract changed after approval; event replay prevents stale map state after reconnect; authorization-aware updates prevent leaking private repo or security-review nodes to the wrong users.

The compromise is a hierarchical map backed by a richer typed substrate. The UI can choose simplified views, but the backend should not erase semantics. Start with fewer visible node types while preserving detailed metadata and edge categories for filtering, policies, and future views.

## 5. GitHub

Opus proposes OAuth only for v1, no GitHub App. No permission syncing tables. No background refresh.

This is the area where Opus’s simplification is most likely to hurt production early. GitHub integration is not just login. For an AI orchestration engine, GitHub is the source of truth for repos, branches, PRs, checks, reviews, installations, permissions, webhooks, and mergeability. OAuth-only can be acceptable for a personal tool. It is a weak foundation for organization-level automation.

OAuth answers: “which user authorized Cortex?” A GitHub App answers: “which organization or repository installed Cortex, with what permissions, and receiving which events?” Those are different trust models. Cortex needs the second one if it will operate across repos and teams.

At 5 users, OAuth-only may work. Each user connects GitHub, Cortex acts on their behalf, and the team understands the limits. If the first product slice is read-only repo analysis or user-triggered PR creation, OAuth can ship faster. No permission syncing is acceptable if Cortex checks permissions live for each sensitive action. No background refresh is acceptable if stale data is not dangerous.

At 20 users, OAuth-only starts causing ownership and reliability problems. Whose token creates branches? Whose token comments on PRs? What happens when that user leaves the org, changes permissions, revokes OAuth, or hits rate limits? How does Cortex know which repos it is allowed to access? How does it receive webhook events reliably? How does it avoid using a stale permission snapshot? Without permission tables, the app cannot explain why a user or agent could perform an action at a given time.

At 100 users, OAuth-only becomes operationally fragile and hard to audit. Organization admins expect GitHub Apps for repo-scoped installation, least privilege, webhook delivery, and centralized control. User OAuth tokens create ambiguous authority. If Cortex merges a PR using Alice’s token, was that Alice’s action, Cortex’s action, or an agent acting under Alice’s delegated authority? If Alice loses access, do all automations fail? If a repo is added to the org, how does Cortex discover it? If a permission is removed, how quickly does Cortex stop acting?

No permission syncing tables is also dangerous. Cortex does not necessarily need to copy every GitHub permission constantly, but it needs a local authorization model and audit trail. It should know repo installation state, granted scopes, user linkage, team membership or effective role when relevant, last verified time, and action authorization evidence. Live checks alone are not enough because they are slow, rate-limited, and poor for historical audit. Local tables alone are not enough because they can be stale. The right answer is cached permission state with freshness rules and live revalidation for sensitive actions.

No background refresh means Cortex will operate on stale repo and PR state unless every action synchronously fetches everything. That does not scale. Background refresh is how the system keeps mergeability, checks, branches, installations, and permission state current. Webhooks help, but webhooks are not a complete state store. Events can be missed, delayed, redelivered, or arrive out of order. Background reconciliation is the safety net.

Where production failures happen: Cortex thinks a PR is mergeable based on stale state; a user loses repo access but Cortex still allows an action from cached session state; an OAuth token expires and blocks all automation under a goal; a renamed repo breaks orchestration because there is no installation sync; a webhook delivery is missed and Cortex never notices a required check failed; a user asks “why did Cortex push to this repo?” and the system cannot answer with a durable authority chain.

A GitHub App also matters for least privilege. OAuth scopes are often broad. GitHub Apps can be installed on selected repos with specific permissions. For an AI agent system, this is not a nice-to-have. Users will be more comfortable granting a GitHub App access to selected repos than giving broad OAuth scopes to act as a human.

Where Opus is right: OAuth-only is faster for v1 if the v1 is narrow. If Cortex needs user identity, login, and maybe user-authorized read operations, OAuth is fine. Do not block all development on a full GitHub App integration if no automation depends on it yet. But if Cortex will create branches, open PRs, comment, review, merge, or coordinate across org repos, GitHub App support should arrive very early. It is foundational, not enterprise polish.

The best compromise is staged: OAuth for identity and user linking; GitHub App for repo installation and automation authority. Add minimal permission tables from the start: installations, repos, user links, effective access snapshots, token freshness, webhook cursor/reconciliation state. Add background refresh for installation/repo/PR/check state, even if the first version is simple.

## Cross-Cutting Failure Modes

The common pattern in Opus’s proposal is that it optimizes for a small team using Cortex as an assistant, not for a larger team using Cortex as an orchestration control plane. That distinction matters.

At 5 users, humans are the real consistency layer. They remember which repo owns a contract. They know that a certain file is risky. They notice when a question should block work. They can manually inspect GitHub permissions. Cortex can be simple because the organization is simple.

At 20 users, social memory weakens. People specialize. Agents operate in parallel. Some work happens asynchronously. The system needs to encode more intent because the right human is not always watching. A design that relies on informal interpretation starts producing coordination misses.

At 100 users, informal interpretation fails. The system needs auditability, policy, permissions, typed dependencies, and reliable state reconciliation. The problem is not just scale in traffic. It is scale in ambiguity. More users means more concurrent branches, more repos, more partial context, more stale assumptions, more permission changes, more review states, and more release combinations.

The richer design prevents production failures by preserving distinctions that matter under concurrency: path versus symbol versus contract; advisory dependency versus blocking release edge; urgent message versus scoped execution gate; visible graph node versus critical-path hint; user identity versus app installation authority.

But the richer design can also fail if it ships as an overbuilt framework with no real workload. If every detector, edge type, permission state, and chat lifecycle must be perfect before Cortex runs, Opus’s team will ship nothing. The resolution is not “simple” versus “rich.” It is “simple visible v1 backed by extensible, policy-aware primitives.”

| Background refresh | None | Simpler v1 | Fine if low stakes | Stale PR/check state | Missed webhooks and stale mergeability | Needed for reconciliation | Add webhook ingestion plus periodic reconciliation |

Final position: Opus is right about the direction of shipping: smaller visible surface, fewer concepts exposed to users, and no speculative mega-framework. Opus is wrong where simplification deletes distinctions that Cortex will need for safety, auditability, and concurrency. The winning architecture is not maximal complexity. It is a small v1 API backed by extensible typed primitives, so Cortex can start simple without trapping itself in a model that fails as soon as real orchestration begins.
