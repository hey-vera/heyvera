# HeyVera Frontend Master Plan

This is the main planning document for the refreshed frontend lane.

## Product Worldview

HeyVera should become one living surface with multiple related regions.

It should not become:
- a disconnected set of microsites
- a brochure with an unrelated app later
- a crypto-first destination
- a generic AI chat product

The correct model is:
- public mode now
- deeper signed-in mode later
- one shared visual language
- one shared information architecture

## Stable Product Truth

Keep these truths steady:
- Soma is the continuity, identity, authority, and proof substrate
- Vera is the shared intelligence fabric
- HeyVera is the stewarded human-facing surface
- crypto is a proving-ground region, not the metaphysical center
- offline-first local truth plus online-shared legitimacy is a real
  architectural principle

## Frontend Goal

Create a frontend system that is:
- understandable to first-time visitors
- understandable to a first-time vibe coder
- strong enough to feel 10/10
- flexible enough to absorb future backend truth without major rewrites

## Surface Model

Think in layers:

### Layer 1 - Public mode

The first thing people see at `heyvera.org`.

Jobs:
- explain the product
- establish the visual language
- preview the region model
- invite the right early users in

### Layer 2 - Signed-in mode

The later working surface.

Jobs:
- help the user work with their agent
- make identity and proof legible
- make network and discovery feel native
- contain markets as one region, not the center of the world

### Layer 3 - Public proof and discovery surfaces

Read-only or lightly interactive surfaces that can later expose public
identity, proof, discovery, and market-adjacent context.

## Region Model

The long-run HeyVera surface should converge around these regions:
- `Work`
- `Network`
- `Discover`
- `Proof`
- `Identity`
- `Markets`

Optional signed-in overview:
- `Home` as an overview state, not the product worldview itself

### Region Meaning

`Work`
- the user and agent doing real work together

`Network`
- people, guilds, social participation, shared learning context

`Discover`
- exploration of agents, people, capabilities, proofs, and later market
  surfaces

`Proof`
- receipts, lineage, verification, public and private evidence

`Identity`
- account, continuity, delegation, wallet authority, credentials

`Markets`
- payment, wallet, proving-ground crypto, economic experiments

## How The Public Site Relates To The Regions

The public site should not expose all regions as full product screens.
It should hint at them in a disciplined way.

Mapping:
- Hero introduces the living surface idea through one strong preview
- Problem explains why rented assistants are inadequate
- Surface map shows the major regions
- Pillars explain the logic beneath the regions
- How it works grounds the experience in the user-agent loop
- Founding network introduces the social layer without making it the
  whole identity

## Reuse Boundaries

Reuse from ClawNet:
- dark surface discipline
- spacing confidence
- terminal credibility
- infrastructure seriousness

Reuse from Pulse carefully:
- social and discovery instincts
- livelier network thinking

Do not inherit directly:
- dashboard-first IA
- old ceremony/admin language
- purple-heavy styling
- marketplace-first worldview

## Build Order

1. Freeze the public-site thesis
2. Build the public mode
3. Review whether it truly feels like the front door to a larger world
4. Freeze the signed-in shell truth
5. Wire only the regions supported by real backend seams
6. Design later regions without pretending they are already shipped

## Immediate Working Rule

Until the public site is approved:
- do not build the signed-in shell
- do not build extra public routes
- do not turn the site into a dashboard preview
