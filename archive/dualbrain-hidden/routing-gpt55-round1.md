**Round 1 Position**
The Cortex routing intelligence layer should be a constrained learning system, not an autonomous optimizer.

That distinction matters. Cortex should learn which model, provider, strategy, prompt shape, and verification pattern works best for a given task context. But it must never learn its way around privacy, budget, auth, tenant isolation, or the minimum evidence required to claim success. The dial controls resource investment. It does not control truthfulness, safety, or policy.

The hardest problem is reward attribution. Most naive routing systems will learn from the wrong signals: user clicks, agent-written tests, superficial “done” messages, or short-term latency wins. Cortex needs an Evidence Graph that records what was attempted, what verification happened, what changed later, and which actors may have biased the signal. The routing learner consumes that graph through a conservative attribution pipeline.

I would design Cortex around three systems:

1. Evidence Graph and Reward Attribution
2. Invariant Policy and Learned Routing Boundary
3. Dial-to-Strategy Mapping with Subscription Capacity Control

The systems are separate on purpose. Mixing them creates subtle failures. If the dial mapper owns privacy decisions, dial 10 eventually becomes “send more code everywhere.” If the learner owns the evidence floor, it eventually learns that users often accept weak answers. If the capacity tracker owns quality decisions, it eventually optimizes for whoever has available quota rather than whoever is best.

---

## 1. Reward Attribution

### Strong Position

Cortex should not train directly on “success” as a single event.

It should train on attributed evidence slices: compile result, test result, static analysis, review outcome, user acceptance, production incident, revert, follow-up fix, and elapsed stability window. Each slice has provenance, delay, confidence, contamination risk, and affected code scope.

The reward model should be conservative:

- Objective external signals dominate subjective signals.
- Signals generated by the same agent that produced the patch are discounted.
- User approval is weak unless paired with objective verification or later stability.
- Delayed negative evidence can partially rewrite earlier positive credit.
- No-test repositories should not become “easy.” They should become “lower observability.”
- Docs and refactoring tasks still need evidence, but the evidence type changes.
- The learner should not update from evidence that was heavily shaped by the routing decision itself without counterfactual controls.

### Core Concepts

Cortex routes a task by creating one or more attempts. An attempt may be a single model call, a model-plus-reviewer workflow, a parallel fleet, a patch-generator plus verifier, or a staged plan/implement/test sequence.

The Evidence Graph records:

- The task and its context.
- The route chosen.
- The candidate attempts.
- Artifacts produced.
- Verification events.
- User events.
- Later repository events.
- Attribution edges from outcomes back to attempts, models, strategies, and context features.

The learner should not consume raw events. It consumes normalized attribution updates produced by a reward attribution pipeline.

### Signal Taxonomy

Signals should be divided into tiers.

Tier 0: Policy and eligibility signals  
These are not rewards. They decide whether an attempt was valid.

Examples:

- Provider authorization succeeded.
- Privacy policy allowed provider use.
- Budget cap allowed route.
- Required repository scope was available.
- User constraints were honored.
- Model produced output in required format.
- Execution sandbox was valid.

These should not produce positive learning reward. Violating them produces hard negative routing eligibility, not “less preference.”

Tier 1: Hard objective task signals  
These are the strongest positive or negative signals.

Examples:

- Existing test suite passed.
- Compiler/typechecker passed.
- Linter or formatter passed when relevant.
- Build passed from clean checkout.
- Integration test passed.
- Reproduction test failed before patch and passed after patch.
- Runtime smoke test passed.
- Security scanner passed for a security-sensitive patch.
- Migration applied cleanly and rolled back cleanly.
- Patch applied cleanly without conflicts.
- Generated code ran in the target environment.

Tier 2: Independent verification signals  
Strong, but slightly below hard objective signals.

Examples:

- Separate verifier model found no blocking issue.
- Human reviewer approved after reading diff.
- CI passed after branch push.
- Maintainer merged PR.
- Static semantic checker validated behavior.
- Golden snapshot or benchmark remained within tolerance.
- Canary deploy succeeded.

Tier 3: Stability signals  
Delayed but important.

Examples:

- No revert after 1 day, 7 days, 30 days.
- No follow-up bugfix touching same lines.
- No production incident linked to patch.
- No test flake introduced.
- No user reopened issue.
- No rollback after deployment.
- Reduced future failure rate in same area.

Tier 4: Weak subjective signals  
Useful only as auxiliary evidence.

Examples:

- User clicked accept.
- User said “looks good.”
- User copied output.
- User stopped interacting after answer.
- Agent self-reported success.
- Plan looked plausible.
- Generated tests passed.
- Documentation “felt clear” to reviewer.

Tier 5: Negative contamination signals  
These reduce confidence in otherwise positive evidence.

Examples:

- Tests were written by the same model that wrote the implementation.
- Verifier saw the implementation before writing the test.
- User accepted without running anything.
- Patch only changed generated snapshots.
- Route selected an overpowered fleet for a trivial task.
- Repo had no test or build command discovered.
- Evaluation target was ambiguous.
- Same model acted as generator and judge.
- Provider had degraded service.
- Tool logs were truncated.
- Build used dirty workspace with unrelated changes.
- Evidence came from a branch that later diverged significantly.

### Delayed Signal Handling

Cortex needs event-time attribution, not just request-time reward.

A route is chosen at time `t0`. Immediate events arrive seconds later. CI arrives minutes later. Merge maybe hours later. Revert maybe days later. Production incidents may arrive weeks later.

Credit should flow over this execution graph.

If the selected patch passes tests:

- Generator receives primary positive credit.
- Planner receives partial credit if its plan was used.
- Reviewer receives credit if it caught issues or approved a correct patch.
- Arbiter receives credit if it selected the winning candidate.
- Losing parallel candidates may receive neutral or slight negative credit depending on whether they were invalid, worse, or simply unused.

If selected patch fails:

- Generator receives primary negative credit.
- Reviewer/verifier receives negative credit if it approved the failed patch.
- Arbiter receives negative credit if it selected a bad candidate over a good one.
- Unselected candidate that would have passed can receive positive counterfactual credit if verified.

### Avoiding Learning From Garbage

Garbage evidence comes from bad provenance, circular verification, ambiguous tasks, and self-confirming workflows.

Cortex should compute an evidence quality score before updating beliefs.

```rust
#[derive(Debug, Clone)]
pub struct EvidenceQuality {
    pub objectivity: f64,
    pub independence: f64,
    pub reproducibility: f64,
    pub scope_match: f64,
    pub contamination: f64,
    pub observability: f64,
}

impl EvidenceQuality {
    pub fn effective_confidence(&self, base_confidence: f64) -> f64 {
        let positive =
            self.objectivity
            * self.independence
            * self.reproducibility
            * self.scope_match
            * self.observability;

        let contamination_multiplier = 1.0 - self.contamination.clamp(0.0, 0.95);
        (base_confidence * positive * contamination_multiplier).clamp(0.0, 1.0)
    }
}
```

Independence is central. A test written by the same agent that wrote the code is useful, but not strong. A test written by another model from only the issue description is stronger. An existing test is stronger still. A reproduction test that failed before and passes after is strongest.

```rust
            p += 0.20;
        }
        if self.truncated_logs {
```

The attribution pipeline should drop evidence below a minimum quality threshold for positive updates, but keep weak evidence for negative alerts.

```rust
pub enum EvidenceDecision {
    UseForLearning,
    UseForAuditOnly,
    UseForNegativeOnly,
    RejectMalformed,
}

pub fn classify_evidence_for_learning(
    kind: SignalKind,
    quality: EvidenceQuality,
) -> EvidenceDecision {
    let confidence = quality.effective_confidence(default_signal_weight(kind).confidence);

    if confidence < 0.10 {
        return EvidenceDecision::UseForAuditOnly;
    }

    if default_signal_weight(kind).reward < 0.0 && confidence >= 0.15 {
        return EvidenceDecision::UseForLearning;
    }

    if confidence >= 0.25 {
        EvidenceDecision::UseForLearning
    } else {
        EvidenceDecision::UseForAuditOnly
    }
}
```

Negative evidence is allowed through at lower confidence because silent failure is worse than slow learning. But even then, it should be weighted by confidence and cause classification.

### User Approval Is Weak

User approval should not be ignored. For vibe coders, it may be the only frequent signal. But it should never dominate.

User approval means one of these:

- The answer matched the user’s immediate expectation.
- The patch looked plausible.
- The user did not notice a defect.
- The user was satisfied enough to move on.

That is not correctness.

Use user approval mostly for:

- Preference learning.
- Interaction style.
- Provider latency tolerance.
- Plan readability.
- Whether the route was pleasant enough.
- Weak task completion evidence in low-risk contexts.

Separate user preference reward from correctness reward.

```rust
#[derive(Debug, Clone)]
pub struct RewardVector {
    pub correctness: f64,
    pub usefulness: f64,
    pub cost_efficiency: f64,
    pub latency: f64,
    pub user_preference: f64,
    pub policy_compliance: f64,
}

impl RewardVector {
    pub fn scalar_for_model_selection(&self, weights: RewardObjectiveWeights) -> f64 {
        self.correctness * weights.correctness
            + self.usefulness * weights.usefulness
            + self.cost_efficiency * weights.cost_efficiency
            + self.latency * weights.latency
            + self.user_preference * weights.user_preference
            + self.policy_compliance * weights.policy_compliance
    }
}

#[derive(Debug, Clone)]
pub struct RewardObjectiveWeights {
```

### Agent-Written Tests Are Suspect

Agent-written tests are useful in two cases:

1. They are generated before seeing the implementation.
2. They are independently verified against pre-patch failure and post-patch success.

The ideal workflow for bugfix tasks:

1. Model A reads issue and writes reproduction test only.
2. Run test before patch; it should fail.
3. Model B writes implementation.
4. Run same test after patch; it should pass.
5. Existing suite passes.
6. Optional model C reviews.

This is high-quality evidence because the test was created before the patch and proved the bug existed.

For feature tasks, generated tests are weaker because “before fails” may simply mean feature missing. Still useful, but lower weight.

### Bootstrapping No-Test Repos

No-test repos are common among solo coders. Cortex should handle them without pretending confidence is high.

Bootstrapping strategy:

1. Discover project shape.
2. Find build, lint, typecheck, start, and smoke-test commands.
3. Create a repo observability profile.
4. Use cheap syntax and compile checks when possible.
5. Use targeted generated checks.
6. Ask for permission before adding durable test infrastructure.
7. Maintain lower confidence until objective signals exist.

### Tasks With No Objective Signal

Docs, refactoring, naming cleanup, comments, and architectural advice need different evidence.

Docs evidence:

- Links resolve.
- Referenced symbols exist.
- Examples compile or execute.
- Commands are valid.
- Docs match current code signatures.
- Broken anchors reduced.

- Constraints captured.

### Preventing Feedback Loops

The learner can create feedback loops if it always routes to the current favorite model and then only observes evidence for that model. It can also create loops if stronger models get harder tasks and then appear worse.

Cortex needs exploration, counterfactual evaluation, and difficulty normalization.

#### Problem 1: Winner-Takes-All Starvation

If GPT wins early, Claude gets fewer attempts, so GPT gets more learning opportunities.

Solution: constrained exploration.

At low dial, exploration must be cheap. At high dial, exploration can include shadow evaluation.

```rust
#[derive(Debug, Clone)]
pub enum ExplorationMode {
    None,
    CheapShadowReview,
    ShadowPlanOnly,
    ParallelCandidate,
    FullCounterfactual,
}

pub fn exploration_mode(dial: Dial, risk: RiskClass, budget: BudgetState) -> ExplorationMode {
    if budget.is_tight() {
        return ExplorationMode::None;
    }

    match (dial.value(), risk) {
        (1..=2, _) => ExplorationMode::None,
        (3..=4, RiskClass::Low) => ExplorationMode::CheapShadowReview,
        (5..=6, RiskClass::Low | RiskClass::Medium) => ExplorationMode::ShadowPlanOnly,
        (7..=8, _) => ExplorationMode::ParallelCandidate,
        (9..=10, _) => ExplorationMode::FullCounterfactual,
        _ => ExplorationMode::CheapShadowReview,
    }
}
```

### Attribution Pipeline Algorithm

High-level algorithm:

1. Ingest evidence event.
2. Validate schema and provenance.
3. Compute evidence quality.
4. Decide learning eligibility.
5. Link event to artifacts and attempts by scope and graph edges.
6. Compute causal assignments.
7. Convert assignments into reward vector deltas.
8. Apply delayed correction rules.
9. Append attribution updates.
10. Update materialized beliefs.
11. Emit route-learning diagnostics.

Pseudo-Rust:

```rust
pub struct AttributionEngine<Q, C, B> {
    pub quality_model: Q,
    pub credit_assigner: C,
    pub belief_store: B,
}

impl<Q, C, B> AttributionEngine<Q, C, B>
where
    Q: EvidenceQualityModel,
    C: CreditAssigner,
    B: BeliefStore,
{
    pub fn ingest(
        &mut self,
        route: &RouteExecution,
        event: EvidenceEvent,
        artifacts: &ArtifactStoreView,
    ) -> anyhow::Result<Vec<AttributionUpdate>> {
        let quality = self.quality_model.score(route, &event, artifacts)?;
        let decision = classify_evidence_for_learning(event.kind, quality.clone());

        match decision {
            EvidenceDecision::RejectMalformed | EvidenceDecision::UseForAuditOnly => {
                return Ok(vec![]);
            }
            EvidenceDecision::UseForNegativeOnly
                if default_signal_weight(event.kind).reward >= 0.0 =>
            {
                return Ok(vec![]);
            }
            _ => {}
        }

        let assignments = self.credit_assigner.assign(route, &event, artifacts)?;
        let base = default_signal_weight(event.kind);
        let effective_confidence = quality.effective_confidence(base.confidence);

        let mut updates = Vec::new();

        for assignment in assignments {
            let attempt = route
                .attempts
                .iter()
                .find(|a| a.id == assignment.attempt_id)
                .ok_or_else(|| anyhow::anyhow!("missing attempt"))?;

            let delta =
                base.reward
                * assignment.causal_weight
                * assignment.confidence
                * effective_confidence;

            let update = AttributionUpdate {
                update_id: uuid::Uuid::new_v4(),
                task_id: route.task_id,
                attempt_id: attempt.id,
                route_id: route.route_id,
                model_id: attempt.model,
                strategy_id: attempt.strategy,
                event_id: event.id,
                reward_delta: delta,
                confidence_delta: effective_confidence,
                credit_window: classify_credit_window(event.event_time, route),
                reason: AttributionReason::EvidenceEvent(event.kind),
                created_at: time::OffsetDateTime::now_utc(),
            };

            self.belief_store.append_update(update.clone())?;
            updates.push(update);
        }

        Ok(updates)
    }
}
```

### Belief Update Algorithm

Use contextual bandits, not global leaderboards.

For each route arm, maintain posterior estimates by context bucket. A practical first version can use Bayesian linear regression or Thompson sampling with handcrafted features. Start simple: hierarchical contextual Thompson sampling.

Global prior:

- Provider/model general quality.
- Strategy general quality.
- Task family quality.
- Repo language quality.

Tenant prior:

- User/team-specific preferences and repo-specific outcomes.

Repo prior:

- Local style, framework, test ecosystem.

Belief hierarchy:

```rust
#[derive(Debug, Clone)]
pub struct HierarchicalBelief {
    pub global: RouteBelief,
    pub tenant: Option<RouteBelief>,
    pub repo: Option<RouteBelief>,
    pub context: Option<RouteBelief>,
}

impl HierarchicalBelief {
    pub fn blended(&self) -> RouteBelief {
        let mut total_weight = 0.0;
        let mut mean = 0.0;
        let mut uncertainty = 0.0;

        for (belief, weight) in [
            (&self.global, 1.0),
            self.tenant.as_ref().map(|b| (b, 2.0)).unwrap_or((&self.global, 0.0)),
            self.repo.as_ref().map(|b| (b, 3.0)).unwrap_or((&self.global, 0.0)),
            self.context.as_ref().map(|b| (b, 4.0)).unwrap_or((&self.global, 0.0)),
        ] {
            if weight > 0.0 {
                let effective = weight * belief.effective_sample_size.max(1.0).sqrt();
                total_weight += effective;
                mean += belief.mean_reward * effective;
                uncertainty += belief.uncertainty * effective;
            }
        }

        RouteBelief {
            key: self.global.key.clone(),
            mean_reward: mean / total_weight.max(1.0),
            uncertainty: uncertainty / total_weight.max(1.0),
            evidence_count: self.global.evidence_count,
            effective_sample_size: total_weight,
            last_updated_at: time::OffsetDateTime::now_utc(),
        }
    }
}
```

Use Thompson sampling during selection:

```rust
pub trait RouteScorer {
    fn score_candidate(
        &self,
        candidate: &RouteCandidate,
        context: &RoutingContext,
        rng: &mut dyn rand::RngCore,
    ) -> f64;
}

pub struct ThompsonRouteScorer {
    pub exploration_temperature: f64,
}

impl RouteScorer for ThompsonRouteScorer {
    fn score_candidate(
        &self,
        candidate: &RouteCandidate,
        context: &RoutingContext,
        rng: &mut dyn rand::RngCore,
    ) -> f64 {
        let belief = candidate.belief.blended();
        let sampled_quality = sample_normal(
            belief.mean_reward,
            belief.uncertainty * self.exploration_temperature,
            rng,
        );

        let expected_cost_penalty = context.cost_weight * candidate.estimated_cost.normalized();
        let expected_latency_penalty =
            context.latency_weight * candidate.estimated_latency.normalized();

        sampled_quality - expected_cost_penalty - expected_latency_penalty
    }
}
```

For early versions, a deterministic upper-confidence-bound variant may be easier to debug:

## 2. Learned vs Invariant

### Strong Position

Cortex must implement hard policy gates before route scoring. The learner receives only candidates that already satisfy invariants.

The selection stack should be:

1. User/org/repo constraints.
2. Provider auth and entitlement constraints.
3. Privacy and data residency constraints.
4. Budget and capacity constraints.
5. Evidence floor constraints.
6. Risk-specific verification constraints.
7. Learned route scoring.
8. Dial-based investment expansion.
9. Final transparency/audit record.

The learner must not be able to override steps 1-6.

### What Is Learned

The following should be learned:

- Which provider/model performs best for task family and repo profile.
- Which route template works best: single model, planner-implementer, generator-reviewer, parallel candidates, test-first, verifier loop.
- Which model is best at each role: planning, coding, review, tests, explanation.
- How much parallelism is worth it for a task type under a dial setting.
- Which verification strategy finds real issues.
- Which prompt template performs best.
- Which context packing strategy works best.
- Which model handles a language/framework better.
- Which model is faster or more reliable for a tenant.
- Which model tends to over-edit.
- Which strategy tends to produce patches that later revert.
- Which provider is degraded right now.

### What Is Invariant

The following should be invariant:

- Privacy constraints.
- Provider authorization.
- Tenant boundaries.
- User provider locks.
- Budget hard caps.
- Legal/compliance constraints.
- Data residency constraints.
- Secret handling.
- Evidence floor.
- Minimum independence requirements for high risk.
- Claims policy: what Cortex may say is verified.
- Maximum blast radius per task without explicit approval.
- Human approval requirements for critical actions.
- Rate-limit respect.
- Audit logging.
- Sandbox restrictions.

### Subtle Boundaries

#### “Auth Code Needs Stronger Verification”

This should be invariant at the risk classification layer, not learned.

The learner can learn that some auth tasks are easier than others, or that a particular model is good at auth code. But the rule “auth-sensitive code requires stronger verification” must not be learned from outcomes. It is a risk policy.

Reason: auth bugs are asymmetric. The absence of reported failures is weak evidence. Users may not notice vulnerabilities. A route optimizer trained on user acceptance will under-verify auth changes because the negative signal is rare and delayed.

So:

- Auth sensitivity detection can be learned-assisted.
- Auth risk classification threshold is policy-configured.
- Verification floor for auth-sensitive tasks is invariant.
- Route choice within that floor is learned.

Rust:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum RiskClass {
    Low,
```

#### “Dial 10 Uses All Providers”

This is not invariant. It is a preference bounded by constraints.

Dial 10 means maximum allowed investment within budget, privacy, provider auth, and capacity. If a provider is disallowed by privacy or lacks auth, dial 10 cannot use it. If evidence floor requires independent review and only one provider is available, Cortex can use another model from same provider, but must lower independence confidence and say so.

#### “Budget Cap”

Hard budget cap is invariant. Budget preference is learned/configured.

- “Never spend more than $50/month” is invariant.
- “Prefer cheap unless quality improves materially” is dial/scoring.
- “This repo can use dial 8 during business hours” is configured policy.
- “This task seems worth extra spend” is learned preference only within caps.

#### “Route Templates”

Route templates should be configured primitives with learned selection and discovered variants.

Do not let the learner invent arbitrary execution graphs directly in production. That is too hard to audit. Instead:

- Humans define safe route template schemas.
- Cortex can instantiate templates with model choices.
- Cortex can learn template selection.
- Cortex can discover candidate templates offline or in shadow mode.
- Promotion of new template families requires config/proposal in product governance.

### Dial as Constraint or Preference?

The dial is both, but at different layers.

Dial as constraint:

- Upper bound on route investment.
- Maximum parallelism.
- Maximum paid token spend per task.
- Maximum number of verifier passes.
- Maximum use of scarce subscription slots.
- Maximum latency budget unless user opts into waiting.

Dial as preference:

- Cost/quality tradeoff inside the allowed range.
- Exploration temperature.
- Willingness to launch shadow candidates.
- Willingness to use premium models.
- Willingness to run extra verification beyond floor.
- Willingness to wait for cooldown rather than fallback.

Dial must never lower evidence floor. Dial 1 still needs enough verification to avoid false claims. Dial 10 may exceed the evidence floor with extra review, parallelism, and stress checks.

### Policy Evaluation Before Learning

Candidate route generation:

```rust
pub struct RoutingEngine<P, C, L> {
    pub policy: P,
    pub capacity: C,
    pub learner: L,
}

impl<P, C, L> RoutingEngine<P, C, L>
where
    P: InvariantPolicy,
    C: CapacityTracker,
    L: LearnedRouter,
{
    pub fn choose_route(&self, request: RoutingRequest) -> anyhow::Result<RoutePlan> {
        let policy_decision = self.policy.evaluate(&request);

        if !policy_decision.allowed {
            return Ok(RoutePlan::blocked(policy_decision.hard_blocks));
        }

        let candidates = generate_route_candidates(
            &request,
            &policy_decision.constraints,
            &policy_decision.evidence_floor,
        );

        let capacity_filtered = self.capacity.filter_available(candidates, &request)?;

        let feasible = apply_dial_limits(
            capacity_filtered,
            request.dial,
            &policy_decision.constraints,
        );

        let selected = self.learner.rank_and_select(
            feasible,
            &request,
            &policy_decision.evidence_floor,
        )?;

        Ok(RoutePlan::selected(selected, policy_decision))
    }
}
```

`generate_route_candidates` should include only route templates that can satisfy evidence floor. Dial can reduce optional investment, not required verification.

## 3. Dial-to-Routing Mapping

### Strong Position

The dial should map to an investment envelope, not a model list.

A user with one $20 subscription at dial 10 cannot get the same route as a team with eight $200 subscriptions at dial 10. Dial 10 means “use the maximum useful share of my available pool.” Therefore dial mapping must be capacity-relative.

The flow:

1. Build subscription registry.
2. Observe live capacity.
3. Compute user/team entitlement.
4. Classify task family and risk.
5. Determine evidence floor.
6. Convert dial to investment envelope.
7. Generate route candidates.
8. Filter by privacy/auth/budget/capacity.
9. Score candidates by learned beliefs.
10. Reserve capacity.
11. Execute route.
12. Release/update capacity observations.

### Fair Team Allocation

Fairness should be enforced over scarce subscription capacity, especially when pooled subscriptions are shared by members using different dial levels.

Principles:

- Evidence-floor-required verification gets priority over optional dial expansion.
- A user at dial 10 should not starve a user at dial 3 from basic service.
- Team-owned subscriptions should be allocated by configured weights.
- Personal subscriptions should prefer owner usage unless explicitly shared.
- Background exploration is first to be dropped.
- Interactive tasks outrank speculative shadow candidates.
- High dial buys more optional capacity only after required capacity is satisfied.

Use weighted fair queuing with priority classes.

```rust
pub fn fair_share_score(account: &FairShareAccount, request: &AllocationRequest) -> f64 {
    let priority_boost = match request.priority {
        ReservationPriority::CriticalVerification => 100.0,
        ReservationPriority::EvidenceFloorRequired => 50.0,
        ReservationPriority::HighDialInteractive => 10.0,
        ReservationPriority::NormalInteractive => 5.0,
        ReservationPriority::LowDialInteractive => 3.0,
        ReservationPriority::BackgroundExploration => 1.0,
    };

    let dial_boost = 1.0 + ((request.dial.value() as f64 - 1.0) / 9.0);
    let consumption_penalty =
        account.recent_consumption_units / account.weight.max(0.1);

    priority_boost * dial_boost + account.burst_allowance - consumption_penalty
}
```

Important: dial influences priority among optional work, not invariant verification. A dial 1 security fix still gets required verification if policy demands it, even if optional parallel candidates are skipped.

### Dial x Task Risk Interaction

Risk determines the floor. Dial determines the ceiling and optional extras.

For low risk:

- Dial 1: single cheap model, minimal verification.
- Dial 5: good model plus maybe review.
- Dial 10: multiple candidates if useful, but not wasteful if task is trivial.

For high risk:

- Dial 1: still must satisfy evidence floor, perhaps with one generator and required verifier.
- Dial 5: stronger generator, independent review, tests.
- Dial 10: parallel candidates, independent verifier, stress checks, maybe human review requirement if critical.

Dial should not map linearly to cost. It maps to marginal investment if the task can benefit.

```rust
#[derive(Debug, Clone)]
pub struct InvestmentEnvelope {
    pub max_candidates: usize,
    pub required_verifiers: usize,
    pub optional_verifiers: usize,
    pub allow_parallel: bool,
    pub allow_premium: bool,
    pub allow_wait_for_capacity: bool,
    pub max_estimated_cost: CostBudget,
    pub max_latency: LatencyBudget,
}

pub fn investment_envelope(
    dial: Dial,
    risk: RiskClass,
    pool: &AvailablePoolSummary,
) -> InvestmentEnvelope {
    let base = dial_policy(dial);

    let required_verifiers = match risk {
        RiskClass::Low => 0,
        RiskClass::Medium => 1,
        RiskClass::High => 1,
        RiskClass::Critical => 2,
    };

    let risk_candidate_floor = match risk {
        RiskClass::Low => 1,
        RiskClass::Medium => 1,
        RiskClass::High => 1,
        RiskClass::Critical => 2,
    };

    let max_candidates = base
        .max_parallel_candidates
        .max(risk_candidate_floor)
        .min(pool.max_useful_parallelism);

    InvestmentEnvelope {
        max_candidates,
        required_verifiers,
        optional_verifiers: base.max_verifier_passes.saturating_sub(required_verifiers),
        allow_parallel: max_candidates > 1,
        allow_premium: base.allow_premium_models,
        allow_wait_for_capacity: dial.value() >= 7,
        max_estimated_cost: CostBudget::from_dial(dial, risk, pool),
        max_latency: LatencyBudget::from_dial(dial, risk),
    }
}
```

### Cold-Start Dial

For a brand-new user, dial 5 should not mean “average of learned preferences.” It should mean a deterministic default investment envelope relative to available subscriptions.

Cold-start priors:

- Prefer robust generalist models for coding.
- Avoid exotic route templates until evidence exists.
- Use more verification when repo observability is weak.
- Use exploration carefully at dial 5 and above.

- One independent verifier if capacity allows.
- Use existing build/test commands if discovered.

Mapper algorithm:

```rust
pub struct DialToStrategyMapper<T, S> {
    pub template_registry: T,
    pub scorer: S,
}

impl<T, S> DialToStrategyMapper<T, S>
where
    T: TemplateRegistry,
    S: RouteScorer,
{
    pub fn map(
        &self,
        request: &RoutingRequest,
        policy: &PolicyDecision,
        pool: &AvailablePool,
        rng: &mut dyn rand::RngCore,
    ) -> anyhow::Result<RouteCandidate> {
        let envelope = investment_envelope(
            request.dial,
            policy.evidence_floor.risk,
            &pool.summary(),
        );

        let templates = self.template_registry.templates_for(
            request.task_features.family,
            request.dial,
            policy.evidence_floor.risk,
        );

        let mut candidates = Vec::new();

        for template in templates {
            let instantiated = instantiate_template(
                template,
                request,
                policy,
                pool,
                &envelope,
            )?;

            for candidate in instantiated {
                if !candidate.evidence_satisfies_floor {
                    continue;
                }

                if !within_budget(&candidate, request.hard_budget.as_ref(), &envelope) {
                    continue;
                }

                candidates.push(candidate);
            }
        }

        candidates
            .into_iter()
            .max_by(|a, b| {
                let sa = self.scorer.score_candidate(a, &request.into(), rng);
                let sb = self.scorer.score_candidate(b, &request.into(), rng);
                sa.partial_cmp(&sb).unwrap_or(std::cmp::Ordering::Equal)
            })
            .ok_or_else(|| anyhow::anyhow!("no feasible route"))
    }
}
```

### Execution and Learning Loop

End-to-end:

```rust
pub async fn route_task(
    request: RoutingRequest,
    services: &mut Services,
) -> anyhow::Result<RouteOutcome> {
    let policy = services.policy.evaluate(&request);

    if !policy.allowed {
        return Ok(RouteOutcome::Blocked(policy.hard_blocks));
    }

    let registry = services.subscriptions.for_tenant(request.tenant_id)?;
    let capacity = services.capacity.snapshot(request.tenant_id)?;
    let pool = AvailablePool::build(registry, capacity, &request, &policy)?;

    let mut rng = rand::thread_rng();

    let candidate = services.mapper.map(
        &request,
        &policy,
        &pool,
        &mut rng,
    )?;

    let plan = RoutePlan::selected(candidate, policy.clone());

    let reservations = services.capacity.reserve(
        &plan,
        ReservationPriority::NormalInteractive,
    )?;

    let execution = services.executor.execute(plan).await;

    for obs in execution.capacity_observations() {
        services.capacity.record_observation(obs)?;
    }

    for event in execution.evidence_events() {
        services.attribution.ingest(
            execution.route_execution(),
            event,
            execution.artifacts(),
        )?;
    }

    Ok(RouteOutcome::Completed(execution.final_report()))
}
```

## The Three Systems Together

### System A: Evidence Graph and Reward Attribution

Responsibilities:

- Store route decisions, attempts, artifacts, evidence, and attribution updates.
- Normalize signals.
- Handle delayed evidence.
- Discount contaminated evidence.
- Separate correctness from preference.
- Produce belief updates.

It should not:

- Decide privacy.
- Decide budget.
- Decide evidence floors.
- Directly execute routes.

### System B: Invariant Policy and Learned Boundary

Responsibilities:

- Classify risk.
- Enforce privacy, auth, tenant, budget, and evidence constraints.
- Decide what must be verified.
- Decide what claims are allowed.
- Produce policy decision audit.

It should not:

- Pick the best model among valid candidates.
- Learn to weaken its own constraints.
- Treat user acceptance as a policy override.

### System C: Dial-to-Strategy and Capacity Mapping

Responsibilities:

- Convert dial into investment envelope.
- Understand subscription pool.
- Track capacity and fair sharing.
- Generate feasible candidate routes.
- Ask learned scorer to rank valid candidates.
- Reserve capacity and explain decisions.

It should not:

- Bypass evidence floor.
- Treat dial as truthfulness.
- Hide provider exclusions.

## Defensive Claims Against Round 2 Criticism

### “This Is Too Conservative”

It is conservative where false confidence is dangerous and adaptive where quality can actually be learned. The dial still gives power users full fleet behavior. The conservatism is specifically around claims, evidence, and policy.

### “User Approval Should Matter More”

User approval matters for usefulness and preference, not correctness. In coding tasks, the user often lacks immediate evidence. Optimizing too strongly on approval trains models to sound done.

### “Generated Tests Are Useful”

Yes, but provenance decides how useful. Test-first generated tests with pre/post behavior are strong. Tests generated after seeing the patch by the same model are weak.

### “No-Test Repos Need Practical Help”

Agreed. Cortex should help them, but it should report verification limits. No-test repos are lower observability, not lower risk.

### “Dial 10 Should Always Use Everything”

No. Dial 10 should use the maximum useful allowed capacity. If the task is trivial, full fleet is waste. If privacy blocks providers, full fleet is illegal. If team capacity is scarce, optional exploration should yield to required verification.

### “Static Risk Rules Violate No Static Model Selection”

Risk rules are not model selection rules. “Auth code requires stronger verification” is a safety invariant. The model used for auth work is learned. The minimum verification is not.

### “Route Templates Should Be Learned”

Template selection should be learned. Template primitives should be configured and auditable. Letting the learner invent arbitrary execution graphs is not a responsible production interface for a system that mutates code.

## Minimal Viable Implementation

For v1, implement:

1. Append-only Evidence Graph.
2. Built-in route templates.
3. Policy gate with risk/evidence floors.
4. Subscription registry.
5. Capacity snapshots and reservations.
6. Contextual UCB route scorer.
7. Basic delayed evidence jobs for CI, merge, revert, and follow-up fixes.
8. Route decision audit.

Do not start with a complex neural reward model. Start with transparent scoring and attribution. The hard part is not fitting a function. The hard part is collecting non-garbage evidence with defensible causal links.

A v1 scorer:

```rust
pub fn route_score(candidate: &RouteCandidate, context: &RoutingContext) -> f64 {
    let belief = candidate.belief.blended();

    let quality = belief.mean_reward + context.exploration * belief.uncertainty;
    let cost_penalty = context.cost_weight * candidate.estimated_cost.normalized();
    let latency_penalty = context.latency_weight * candidate.estimated_latency.normalized();

    let capacity_penalty = if candidate.estimated_capacity_units.total()
        > context.capacity_soft_limit
    {
        0.25
    } else {
        0.0
    };

    quality - cost_penalty - latency_penalty - capacity_penalty
}
```

That is enough if the evidence graph is good. A sophisticated learner on bad evidence will be worse than a simple learner on clean evidence.

## Final Architecture Statement

Cortex should route through a layered decision system:

- Invariants decide what is allowed and what must be proven.
- Dial decides how much resource investment is permitted.
- Capacity decides what is currently feasible.
- Learned routing decides which valid strategy has the best expected utility.
- Evidence Graph decides what the system is allowed to learn from afterward.

The key design principle is this:

**The routing learner may optimize investment, model choice, and workflow shape, but it may not optimize away the conditions required for a truthful success claim.**
